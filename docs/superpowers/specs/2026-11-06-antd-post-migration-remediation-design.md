## FP-00 授权、目标和范围

用户在收到规范后回复「可以，继续下一步」，本轮据此编写实施计划。A、B 两批均进入计划范围，实施仍需用户另行明确开工，B 批需明确授权。之前的迁移授权、审查通过、文档提交、聊天恢复和计划批准均不构成此次产品改动的开工指示。

用户要求移除按钮底部浅影、用 Ant Design 组件表达加载、修复下拉文字对齐、让新建海报可以从背景库开始，并统一布局和字体。上一轮审查又定位了缩减动效、手机撤销、编辑事务、分页失败、后台写入和交付文档问题。本规范把审查建议转为可验收的设计。下表列出规划范围和对应的实施边界。

| 批次 | 交付范围                                                  | 独立边界                                                   |
| ---- | --------------------------------------------------------- | ---------------------------------------------------------- |
| A    | FP-01 至 FP-10。修复共享 UI、创作流程、列表和后台界面状态 | 使用现有 API、权限、数据模型和路由。可先独立验收发布       |
| B    | FP-11。修复后台资源版本覆盖和分类部分提交                 | 涉及 IDL、生成代码及服务端事务。需明确纳入授权，可独立交付 |
| 全程 | FP-12 至 FP-14。维护说明、回归证据和交接                  | 每个获准批次必须有自己的验收证据                           |

实施计划分为 [A 批前端和交互](../plans/2026-11-06-antd-remediation-a-implementation.md) 与 [B 批后台资源写入](../plans/2026-11-06-antd-remediation-b-implementation.md)。

优先恢复缩减动效下的操作和手机撤销，再处理选区事务及其他影响数据正确性的缺陷。视觉统一与背景库创建可分开验收。B 批的事务边界独立于视觉问题，A 批通过后仍按实际范围标记 B 批状态。

沿用原布局规范 UI-01 至 UI-14。本规范只覆盖与其明确冲突的细节，例如给「新建海报」增加背景来源选择、为手机恢复历史按钮。原有账号隔离、作品归属、字体字形检查、自动保存、回收站、导出和文档格式继续作为回归契约。两站继续使用 `antd@6.7.0`、共享 `UIProvider` 和 `Editor`。renderer 保持独立。整站重新换风格、更换路由框架、升级组件库、重写编辑器 store 或改变海报渲染规则均在本次范围之外。全局数据库结构和数据迁移也在范围之外，B 批复用现有资源版本模型。

## FP-02 加载、空态和错误

加载状态由真实请求或事务驱动，持续可见的文字说明应具体，例如「正在载入字体」或「正在上传原图」。读屏只需听到一次有意义的状态说明。已有列表刷新时优先保留仍适用于当前查询的内容，并在该区域标记忙碌。上一页、不同筛选或其他账号的数据不能伪装成当前结果。

| 场景                                   | 期望                                                                                                             |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 首次展示作品、模板、背景等可预测网格   | 用 antd `Skeleton`，占位与实际网格几何一致                                                                       |
| 会话、路由、草稿、字体、目录、预览等待 | 用区域内 antd `Spin` 或等价 antd 加载组件，文案跟随实际阶段，避免全局遮罩挡住仍可执行的操作                      |
| 列表或后台表格                         | 保留 antd `Table loading` 或区域 `Spin`，已到达且为空才显示空态                                                  |
| 提交、上传、保存、应用模板             | 操作上用 antd `Button loading`。同时有进度说明时，忙碌只影响相关操作，不形成重复播报                             |
| 导出、待清理、离线                     | 用真实任务状态区分等待、完成、可重试失败、离线。运行中使用 antd 加载组件。后台任务的继续执行与当前对话框状态独立 |
| 查询或操作失败                         | 保留可见的失败原因和当前范围内可操作的重试入口。适合持久提示的错误仍用语义化 Alert                               |

发布前核查用户站、管理站、共享 UI 与编辑器的所有真实等待入口，包括懒加载回退、待清理和导出。等待态禁止复用蓝色信息 Alert、自绘 spinner 或自绘骨架。静态说明、成功、错误及需要人工操作的提示有各自语义。缩减动效时提供静态或减少变化的可识别加载外观，状态文本和忙碌语义继续工作。 [现有 Status](../../../packages/ui/src/Status.tsx) · [Spin](https://ant.design/components/spin/) · [Skeleton](https://ant.design/components/skeleton/)

## FP-03 Select、Combobox 和属性区排版

复用共享 Select/Combobox 的字段几何。闭合态的普通值、搜索输入、占位、色块和箭头沿同一垂直中心线。自动化以可见文字容器和控件中心的差值绝对值 ≤2px 为阈值，并核对箭头。打开态独立验收菜单项的行内对齐、可读性与滚动。保留左右留白、长值截断、空和混合态、色块、禁用项、搜索、键盘高亮和可访问名称。搜索输入、单选行、虚拟列表及嵌套浮层应以实际可见行为验收。字体高亮预览不提交，只有确认选项后才进入既有字形检查。优先使用公开的语义插槽，必要的内部样式限定在共享组件。 [现有 Select 样式](../../../packages/ui/src/Select.module.css) · [Ant Design Select](https://ant.design/components/select/#semantic-dom)

属性区保持「文字 / 段落 / 效果 / 位置」四组。桌面面板和手机抽屉共用字段顺序、标签和辅助说明。标签与控件间 4–8px，字段及相关说明成组，组与组间 12–16px，面板内边距 12–16px。同一层级使用一致的分组方式，减少字段自身外边距与布局 gap 的叠加。空间充足时字号与颜色可并排，过窄时按字段顺序单列。图标命中区和视觉尺寸分开，正常正文、禁用态、混合值和真实校验提示可辨认。标题和状态过长允许截断，键盘和触控入口仍可识别。使用两层色样，透明棋盘在颜色下方，六位 hex 显示为完整实色，八位 hex 依实际透明度混合。界面色样不参与海报文档序列化。

首次修复重点为作品页头部、用户与模板共用工作台、后台同类表单和弹层。保留浅色表面与深绿主操作，把视觉重点留给海报。依照原布局规范核对 1440、1024、768、390、320px 五档。320px 可把低频顶栏动作归入一个具名「更多」入口，返回、作品名或可识别缩略标题、保存状态和导出应有清晰位置。海报属性值、坐标、字重与实际导出不受界面排版影响。

## FP-04 减少动效、弹层生命周期与焦点

从共享 UI 消除全局强制截断动效导致的浮层失效。跟随操作系统 `prefers-reduced-motion`，优先采用 antd 公开的动效配置，应用自身的非必要动效按作用域处理。验收以浮层可见、可操作、正常关闭为准，保留库所需的生命周期和事件。普通动效和缩减动效两种模式都覆盖作品卡片菜单、Select/Combobox、ColorPicker、Modal、Drawer 和提示层。 [现有全局规则](../../../packages/ui/src/styles.css#L122) · [antd 动效配置](https://ant.design/docs/react/customize-theme/#disable-motion)

同一时间只有最上层接收弹层的关闭操作。Escape 先关闭内层菜单，再关闭可取消的父层。关闭后归还焦点，移除滚动锁和失效的弹层注册。手机「背景 → 从背景库选择」属于来源层替换，关闭库后焦点归还仍存在的底栏「背景」。模板全屏编辑器打开时，底层列表和导航退出顺序焦点和交互。内部编辑器仍能使用撤销等快捷键，嵌套弹层打开时归对应弹层处理。关闭全屏工作台采用其显式关闭操作，焦点优先归还打开它的卡片，卡片消失则归列表中有意义的入口。用键盘、真实点击和触控模拟验收，不以 DOM 挂载数量替代可见性与焦点检查。

## FP-05 新建海报与背景库

用户站在作品页保留独立「模板库」，模板、ZIP 导入及跳转照原流程。「新建海报」打开名称明确的来源选择，选项为「上传本地图片」与「从背景库选择」。作品空态的主动作打开同一入口，文件拖放继续直达本地导入。桌面与手机复用同一选择逻辑。选择器打开先聚焦标题或首个合理操作，系统文件选择器由用户点击直接打开，取消后归还焦点且无创建请求。

| 流程       | 规则                                                                                                                                                                                          |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 背景库查询 | 沿用公开目录查询，保留名称、分类、搜索、分页、错误和空态。卡片显示名称、缩略图、原始像素尺寸。空目录提供回到来源选择的路径                                                                    |
| 选中       | 单选，选中后保留明显标识和「用此背景创建」确认动作。改搜索、分类或页码使选中项不再可见时清除选中，避免提交不可见素材。关闭无写入                                                              |
| 创建       | 确认时以当前筛选页重新校验资源仍为同一可见版本，采用返回的素材 ID、资产版本和原始宽高。通过现有 `CreateProject` 新建空白文字文档，默认标题为背景名称，只发送一次提交。成功后打开返回的作品 ID |
| 失效       | 校验失败保留筛选和分页供重试。素材已下架、消失或改版时清除旧选中，显示原因，由用户重新选择确认                                                                                                |
| 已有作品   | 复用背景目录和卡片选择界面，确认按钮写作「替换背景」。同尺寸应用一次。异尺寸沿用已有确认和几何规则，取消不改文档，成功可撤销                                                                  |
| 本地导入   | 保留 40 MiB 与现有格式校验，上传成功后持有素材 ID、版本及尺寸，验证作品标题后创建。可用文件名提取标题，非法或过长时整理成服务端可接受的标题                                                   |

发布目录是新入口的选择依据。当前服务端允许拥有既有作品引用的用户继续使用相应资产，A 批保持这一规则。提交前的目录复查会缩小竞争窗口，资源在复查与创建之间变化时仍以现有服务端授权结果为准。本规范不承诺公开发布状态与创建事务原子绑定。严格绑定需要单独批准服务端契约。直接引用现有资产，无需下载再上传，不改既有作品的引用。 [背景目录](../../../apps/web/src/features/catalog/BackgroundPicker.tsx) · [创建事务](../../../server/internal/projects/service.go#L86) · [引用授权](../../../server/internal/projects/refs.go#L66)

## FP-06 上传和创建的失败恢复

本地链路区分 `等待选择 → 上传 → 已有素材 → 创建 → 已创建`。上传成功后，已拿到的素材 ID 和版本属于当前用户、当前操作。创建明确被拒且可恢复时，在同一操作内重试创建并复用原素材。素材已无权访问时才回到重新选择。请求超时、连接断开或无法判断是否提交成功的服务端错误进入「结果未确认」，给出返回作品列表并重新加载的入口，禁止自动重新提交。现有 API 缺少创建幂等键，页面不能仅凭标题猜测已经创建的作品。这是 A 批的显式限制。永久幂等键和不再使用资产的回收策略留给单独设计。

保存、上传、应用模板及创建的迟到回调以当前账号、当前请求和仍有效的页面操作为约束。退出、切换账号、离开流程后，旧回调不得触发跳转、显示过期提示或进入新账号的列表状态。已在服务端提交的结果留在原账号。按钮、卡片、文件选择、拖放和重试共用提交防重。创建请求发出后流程提示当前状态，关闭或导航不宣称取消了已送达的写入。 [现有上传与重试](../../../apps/web/src/features/projects/ProjectsPage.tsx#L193)

背景库创建、应用模板和导入模板包也会新建作品。它们沿用各自现有的成功路径和明确失败处理，并共用「结果未确认」规则。模板包上传与作品创建由同一接口完成，客户端只在本地图片的两步链路中复用已取得的素材引用。 [模板应用与导入](../../../apps/web/src/features/templates/TemplatePicker.tsx#L133)

## FP-07 手机工作台、画布和操作一致性

390px 和 320px 下，画布工作台提供可点击的「撤销」与「重做」。采用画布工具条中的具名图标，两个操作在可编辑工作台可直接发现，命中区至少 44×44px，禁用随共享历史状态变化。非手机保留原工具栏操作。删除、换背景、移动、样式编辑后，触控用户可恢复最近一次已提交操作。关闭选择器、换断点和调整视图不产生历史项。桌面和手机共享添加文字上限、可用字体、复制、删除、文案忙碌和选区的判断。手机工作台及模板工作台都纳入验收。

手机属性面板打开后，按实际可视画布区域安排选中文字。优先调整视图平移，必要时临时缩放以显示选中范围。文字块过高时至少显示正在编辑的行或选中范围的可用部分，并保留对画布的可操作视口。验收以手机抽屉开启后靠近海报底部的选中文字仍能看到实时变化为准。适应面板高度、键盘和安全区只修改视图。关闭时恢复打开前的手动视图，画布尺寸已变则沿用新尺寸适应逻辑。切换文字块或属性分组不清除文档中的其他选择内容和本地有效修改。 [工作台布局基线](2026-11-05-antd-layout-design.md#ui-06-共享编辑工作台布局) · [画布适配](../../../packages/poster-editor/src/Stage.tsx#L75)

## FP-08 编辑事务、草稿和导出

每一次用户手势由编辑会话统一管理，输入控件和富文本更新只写入该手势所属的范围。打开色板或聚焦属性字段时，未编辑仍显示原保存状态，保存、导出可用性由真实文档和任务状态决定。色板首次有效变化开始一个可撤销事务，同一次打开内的后续变化合并。关闭、失焦关闭或普通 Escape 收起色板时提交已产生的变化。未改则无历史、无新增保存。页面、编辑目标或账号失效时终止旧会话，晚到事件不能作用到新目标。整块、选区和光标三种模式保持既有写入范围。富文本内部延时只处理自身输入，在外部调色或属性事务中不得提前提交该事务。实际变化进行中保留现有保存、导出互斥语义，提交后恢复原自动保存链路。

数字草稿由会话持有，以作品或模板、文字块、属性及编辑目标为作用域。保存原始输入串、会话开始值、最近有效值和对应事务身份。跨断点、面板重新挂载、显示模式变化都能恢复原串和取消基准。输入中的尾随小数点、非法或越界值沿用现有规范。明确按 Escape 恢复**进入该次输入会话之前**的有效值，取消的改动不额外增加历史。用户提交或结束有效输入时按现有时机生效。用按钮或快捷键删除文字块均清除对应草稿。撤销恢复文字块时只恢复文档值。输入法和下拉焦点行为沿用现有约束。历史记录、自动保存、字形预检和导出以同一有效文档和 revision 为准，保存冲突沿用既有恢复策略。 [原数值与选区规则](2026-11-05-antd-layout-design.md#ui-08-数值输入字体及颜色) · [富文本延时提交](../../../packages/poster-editor/src/text/RichTextEditor.tsx#L134)

同一文档内主动换文字块、改变编辑目标或删除前，先在原目标结束手势，有效变更提交一次，未完成的数值串按主动失焦整理。删除产生独立历史，撤销删除恢复最后有效的文档值。仅重排界面、折叠面板或跨断点沿用草稿恢复规则。用户主动离开作品时，有效变更留在原作品的现有本地草稿链路，禁止在页面已失效后额外发起保存。关闭后台模板仍按该工作区现有的显式保存边界处理。会话失效、切换账号或收到作品彻底删除事件时，旧交互立即失效，草稿清理沿用现有账号和删除规则。

## FP-09 列表、分页和改名冲突

成功响应显示当前页已越界时，按服务端总数回到最近有效页。失败或未到达的响应不改变页码。分页状态与结果使用同一账号、筛选和查询身份。错误可见，重试重新请求原页。应用于用户作品、回收站和待清理队列，也应用于后台资源、模板、文案等有相同缩页路径的列表。成功删除导致 25→24 时，自动从第 2 页回到第 1 页。恢复作品页位置应等有效数据和布局到达。切换账号后重置原范围。

改名 A 批沿用 `GetProject` 和 `SaveProject`。打开时保留用户待编辑标题及已观察到的 revision。提交用与该 revision 匹配的完整文档。若发现版本变化或服务端返回冲突，保留用户输入，加载最新版并展示当前标题及用户输入。只有用户在这次冲突提示后再次确认，才允许使用新快照的标题修改、文档和 revision 重新提交。再次冲突时重复该流程。禁止把新 revision 与旧文档拼在一起，禁止同一「重试」反复提交已知无效 revision。删除、换账号或关对话框结束该改名上下文。专用改名端点和列表摘要契约作为后续架构议题保留。 [现有作品页](../../../apps/web/src/features/projects/ProjectsPage.tsx#L141) · [现有保存契约](../../../idl/common/requests.thrift)

## FP-10 管理界面、账号重置和分类查询

密码重置确认发送后，阻止重复提交及对话框内取消、遮罩关闭和 Escape。后台壳层的应用内导航同样不能让执行中的重置结果丢失。成功后在当前管理员的界面中展示一次性令牌，提供复制及明确的「完成」操作，提示有效期。令牌只存在于当前授权会话内存中，不进日志、通知、缓存持久化或测试证据。浏览器刷新、关闭或管理员会话失效时，原令牌不会恢复。响应结果不明时说明旧凭据可能已被撤销，并提示重新核对账号与走现有再次签发流程，禁止自动重置。 [前端重置入口](../../../apps/admin/src/features/Metadata.tsx#L96) · [服务端重置](../../../server/internal/auth/reset.go#L30)

资源筛选和分类下拉能够通过现有分页接口访问第 101 条及以后记录。需要完整层级的文案树，在当前查询作用域读完分类分页再组树，显式处理任何分页失败。缺父节点或分页数据变化时提供可见的重新加载路径。逐页加载失败时不得呈现成完整树。公共背景和模板分类也要能访问后续分类。保持服务端的可见性过滤、五级深度及父子约束。稳定数据下应能展示跨页父子关系。并发修改期间以重新加载完整目录恢复，不要求 A 批提供跨分页事务快照。 [现有文案分类查询](../../../apps/admin/src/features/copy/CopyPage.tsx#L24) · [目录查询](../../../server/internal/catalog/service.go#L98)

公开文案库只读取已发布分类。完整分页成功后，已发布分类若缺少可见父级，在公开树中作为可选的顶层入口，并携带其可见后代，按现有排序展示。保持真实分类 ID 和选取规则。后台应能看到未发布父级，完整读取后仍有缺失时提示目录不完整。此处是本稿选择的展示规则，依据是服务端按每个分类自身的发布状态过滤。 [公开文案组树](../../../apps/web/src/features/catalog/CopyPicker.tsx#L20) · [公开目录过滤](../../../server/internal/catalog/service.go#L114)

## FP-11 后台资源写入边界（B 批）

目标是避免发布动作携带旧内容覆盖新内容，并使分类编辑的移动和字段修改同成同败。本节是对现有服务端契约的定向修复。保持资源 ID、现有资源版本编号格式、公开目录协议、资产引用和管理员权限。实施计划需给出具体 IDL、路由和部署兼容策略，并满足下表的行为契约。

| 操作           | 写入契约                                                                                                                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 创建资源       | 沿用现有创建行为，无历史版本前提                                                                                                                                                                            |
| 保存已有资源   | 客户端提交看到的版本与本次内容。在同一事务锁定资源、比较期望版本、校验、写新版本和引用。不匹配返回可识别冲突，保持服务端数据和本地草稿                                                                      |
| 发布或下架     | 独立写入意图只携带资源 ID、目标发布状态和期望版本。服务端以事务内当前快照为内容来源。若需新版本，完整继承资产版本、内容、元数据及所需资源引用。目标状态已相同且版本匹配时允许成功无写入。过期请求仍返回冲突 |
| 编辑或移动分类 | 改父级、标题、排序和发布状态的一次编辑在单个事务中完成，按既有约束验证类型、循环和整棵受影响子树的深度。独立移动若仍可调用，也必须推进并校验同一冲突版本。失败时所有字段、树和可见版本均无变化              |
| 冲突恢复       | 展示最新版本和动作冲突，保留用户草稿。重新加载确认后以明确的动作重新提交。禁止客户端静默合并、自动覆盖或吞掉冲突                                                                                            |

继续使用当前资源版本作为并发标识，参与上述修改的成功写入均须推进它，版本行和依赖引用随事务更新，保证公开模板引用和资源回读。既有删除及垃圾回收规则继续有效。所有后台调用方随契约同步升级，旧客户端缺少已有资源的版本前提时应失败并提示刷新，避免留下可绕过校验的旧写入路径。必须先改 `idl` 再运行仓库生成流程，部署安排由计划记录。测试验证已有版本可读、已引用资源下架后仍可用、并发只有符合预期版本的写入成功，以及管理员限制。 [现有写入 IDL](../../../idl/common/requests.thrift#L17) · [资源保存事务](../../../server/internal/catalog/service.go#L177) · [分类移动](../../../server/internal/copy/service.go#L82)

现有编辑表单的发布复选框继续参与整份保存。用户在同一次编辑中修改内容和发布状态时，使用同一个期望版本、事务与审计结果。列表或卡片上的「发布 / 下架」走独立发布意图，只提交状态，不携带列表快照的内容。

## FP-12 代码组织、文档和交付

- 共享 UI 统一定义主题、控件密度和加载语义，页面管理业务布局和真实状态来源。任何直接使用 antd 的页面仍使用共享 provider。

- 同批更新 `AGENTS.md`、`README.md`、`deploy/toolchain.lock.json` 和当前验收入口。说明 antd 版本、共享控件与 renderer 边界、后台 B 批契约与兼容范围、创作路径、手机操作和真实测试命令。历史验收记录标明基线及继承关系，避免把旧证据当作新结果。
- 验收依赖的场景、五档检查来源和运行说明必须可从交付版本取得。临时截图、视频和测试数据可保存在明确的证据目录，记录相对路径、生成命令和必要的校验值。业务图片、密码、一次性令牌及真实用户内容不得进入证据。

## FP-14 交接和变更控制

计划应给每个任务建立「需求编号 → 允许修改的边界 → 预期失败用例 → 验收命令 → 交付证据」映射。范围获准后使用单一执行记录，依次记录用户指示、基线、最后验收提交、当前编号、下一步、实际 diff、验证结果和阻塞。上下文压缩或更换执行者后，先恢复最新用户指示和工作区状态，再读 FP-00、当前需求及 FP-13，核对已有 diff、失败场景和实际通过证据后接续。验收矩阵缺项、旧测试误命中或仅截图无法证明交互时，记录为待处理。

布局和控件内部实现可在满足验收条件时裁量。路由、权限、序列化、保存或撤销语义、背景下架授权、后台版本方案与 A/B 批范围属于产品或契约决策。遇到冲突先说明影响，完成范围内独立工作，再把需要决定的项写回规范。设计批准后进入 writing-plans。产品实现以单独明确的开工指示为起点。
