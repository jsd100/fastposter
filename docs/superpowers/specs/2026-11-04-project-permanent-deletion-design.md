# FastPoster 回收站作品彻底删除设计

日期：2026-11-04。状态：独立 builder check 已完成，未发现重要未决问题；用户已回复“确认”，批准本文完整设计，进入实施计划阶段。本文是功能设计，不是实施计划。

## 需求来源与目的

用户要求用户站“回收站”和 `/admin/projects` 中处于回收站状态的作品可以彻底删除，并明确要求相关资源文件也被彻底删除。用户已明确接受：仍被其他作品或资源库引用的素材保留，只删除已无其他引用的相关文件。

用户已体验并认可交互草图：用户回收站与管理端双入口，单件删除确认，管理员额外确认作品归属，文件清理状态、失败重试、导出未结束时阻止删除。草图只模拟状态，不连接业务数据；位于 `.superpowers/brainstorm/9784-1793779277/content/permanent-delete-flow.html`，该目录被 git 忽略。

以下技术方案与明确标记的产品细节是设计者为完成上述需求作出的选择，尚需随本文整体确认，不作为用户逐条指定的要求。

## 范围与非目标

在现有 React/TypeScript、共享 UI/API 包、Go、MySQL、本地 FileStore 架构内完成。两个入口复用同一套删除与清理领域逻辑，权限由各自入口校验。

本期包括：单件彻底删除、独占文件物理清理、持久化重试、清理状态查询、管理员审计、必要迁移和运维接入、相关测试。

本期不包括：批量删除、清空回收站、正常作品直接彻底删除、管理员恢复他人作品、全站定时 GC、强制取消导出、重新设计资源库删除功能。

“彻底删除”指业务记录及托管文件被移除，不承诺磁盘安全擦除，也不删除用户已经下载的文件、其他设备浏览器草稿或历史备份。备份仍按既有保留策略处理。

## 当前实现与约束

- `projects.Service.SoftDelete` 只设置 `deleted_at`；用户列表、恢复仅允许最近 30 天内软删除的作品。
- `catalog.Service.AdminProjects` 返回所有作品的元数据，管理端没有修改作品正文或读取私有图片的能力。
- 现有 `maintenance gc -apply` 在维护模式与独占写锁下运行，清除超过 30 天的作品，并回收不再引用且符合宽限期的素材与文件。它不是自动定时任务，不能作为在线删除的及时执行机制。
- `project_revisions` 随作品行级联删除；`export_jobs` 对作品有非级联外键，必须先处理。
- `asset_refs` 包含 `project`、`project-history`、`export`、资源相关引用。历史引用涵盖作品曾使用过的素材，不能仅从当前文档收集候选。
- 作品复制可能共用相同素材版本；`asset_versions` 保存原图、标准化文件与预览文件 key。版本和父素材行的删除粒度应分开。
- 导出快照解析与导出任务创建当前分属两个事务；在线删除需要补齐跨步骤的状态复查及并发协调。
- 当前工作区已有 `packages/poster-editor/src/panels/color-presets.ts` 的无关修改，实施和提交不得覆盖、混入。

## 产品行为与权限

### 用户回收站

只有作品所有者、账号可用时可发起删除；后端必须再次判断作品归属和 `deleted_at IS NOT NULL`。正常作品调用永久删除接口返回状态冲突，其他用户的作品返回与不存在一致的 `NOT_FOUND`。

回收站卡片在“恢复”之外提供“彻底删除”。确认框显示作品名称，明确“删除后无法恢复”，说明作品、全部历史版本、导出记录及独占资源文件会删除，共享资源会保留。默认焦点在“取消”，禁止重复提交，复用现有 Dialog/Button/Toast。

请求被受理后作品不能恢复或编辑，但仍显示清理进度；刷新、重新登录或切换设备后能找回未完成状态。清理期间可离开页面，任务继续。清理完成后移除状态项，并在当前页面看到成功反馈。

设计者选择：未完成清理信息不受回收站 30 天过滤限制；正常回收站分页与待清理状态不能互相挤掉或错误显示空列表。可用单独的待清理分区，卡片沿用草图的状态视觉，具体组合布局留给实施者。清理项只需名称、作品 ID、尺寸、删除时间和状态，不依赖文档或私有图片继续存在。

### 管理端

管理员可对任意用户已软删除的作品发起彻底删除，包括超过 30 天但尚未经 GC 清理的记录；不能对正常作品执行。权限必须在服务层验证，不能依赖按钮显隐。

`/admin/projects` 增加全部／正常／回收站状态筛选；正常作品无删除按钮。确认框显示作品名称、作品 ID、所有者 ID，并要求勾选“我已确认作品归属，理解此操作会永久删除该用户的作品”。后台继续只展示元数据，不增加正文或私有图片访问权限。

发起删除成功必须与数据库删除在同一事务写审计，例如 `project.permanent-delete`；文件清理完成不能倒推为管理员刚刚操作。重试清理记录独立审计，例如 `project.cleanup-retry`。审计不存正文或私有图片信息。

管理端展示未完成清理状态及重试入口；用户与管理员操作同一个作品时，共用同一个删除任务。管理概览、导出统计在相关数据库行删除后按既有查询自然变化，不另建历史统计系统。

### 导出未完成

设计者选择：存在 `queued` 或 `running` 导出任务时拒绝本次删除，不修改作品、引用或文件，提示“该作品有导出任务尚未结束，请等待完成后再删除”。本期不增加强制取消，也不把请求静默排队到导出结束。

过期 `running` 租约按既有 worker 恢复／失败流程推进；删除接口不能仅因租约过期就忽略仍可能运行的任务。worker 未运行时应如实阻止删除，不伪造完成。

## 数据与文件的删除边界

| 对象 | 处理方式 |
| --- | --- |
| `projects` 主记录、当前文档 | 接受删除事务中移除 |
| 全部 `project_revisions` | 随主记录级联删除 |
| 该作品 `export_jobs`，包含成功和失败任务及快照 | 接受删除事务中移除；存在排队／运行任务则先拒绝整个请求 |
| 作品当前、历史及上述导出的 `asset_refs` | 接受删除事务中解除 |
| 上述导出的 `result_key`、`preview_key` | 持久化后清理实际文件，不等待原 7 天有效期 |
| 当前／历史／导出引用过的素材版本 | 无其他引用时清理，含 original、normalized、preview 非空 key |
| 同一个素材的其他版本 | 分别判断引用，不能整条素材一起删除 |
| `assets` 父行 | 所有版本均已移除才删除 |
| 其他正常作品、回收站作品、历史、导出、资源及资源版本仍引用的素材 | 保留，包括软删除但尚待恢复或 GC 的其他对象 |
| 审计日志 | 保留，不随作品删除 |

引用判定同时覆盖全部 `asset_refs` 与 `resource_versions`，不能只按 `owner_id`、当前文档或发布状态判断。只有最后一个引用消失才能回收共享素材。

直接相关文件不等待现有 GC 的 24 小时宽限期。只处理本作品释放的候选及明确的导出文件，不执行全盘扫描或顺带清理其他孤儿。

相同 key 去重；删除前还须保证该实际 key 没有被其他保留的素材版本或导出使用。沿用 FileStore 的 key 校验和受限根目录，不接受客户端指定磁盘路径。已不存在的文件按清理成功处理。

## 状态、持久化与恢复

### 任务模型

数据库新增持久化删除任务与逐文件工作记录，实际表名、字段名及索引由实施计划确定。必须能表达：

- 删除任务 ID、作品 ID（唯一）、所有者 ID、发起人 ID、发起时间、状态、最近错误、重试时间、执行租约。
- 未完成期间展示所需的最小元数据：名称、尺寸、原软删除时间，不保留作品正文或完整导出快照。
- 候选素材 ID／版本、确定待删除的文件 key、逐项执行结果；进程中断后能继续，而不是依赖内存或已删行来还原 key。
- 任务状态为 `pending`、`running`、`retry_wait`、`completed`。租约过期可以被其他 worker 接管，不永久卡在 running。
- 逐文件状态和候选处理结果保证重复执行安全；所有独占文件清理完毕、共享项判定为保留后，任务才是 completed。

设计者选择：成功任务保留最小任务 ID、作品 ID、所有者 ID、状态与时间，用于重复请求和查询；清空名称、尺寸等展示快照及文件 key、素材候选工作明细。管理员审计独立保留。未完成任务及错误不能因 TTL 自动丢弃。

### 接受删除

在一个数据库事务内：

1. 鉴权；锁定作品并用当前状态检查归属、软删除条件。
2. 检查并协调导出任务的创建、领取和完成；若仍有 queued／running 则无副作用地返回冲突。
3. 收集完整候选素材及其原图／标准化／预览 key，以及导出文件 key，建立唯一删除任务，持久化恢复所需信息；记录 key 只代表候选，不提前决定共享文件可删除。
4. 删除相关导出引用、导出任务、作品引用和作品行；历史级联删除。
5. 管理员发起时写成功审计，然后一起提交。

事务回滚不得留下已接受任务、已解除引用或成功审计。不要通过解析海报正文作为删除的前置条件，以便损坏文档也能从回收站清理。

响应返回任务 ID 及状态，不把“已受理”描述为“文件已删除”。网络丢失响应后，再次请求返回相同任务，不重复创建或重复审计。已存在任务先按持久化 owner／管理员权限检查再返回，不能因作品行已删除放弃鉴权；完全未知 ID 返回 NOT_FOUND。

### 清理执行

事务提交后立即唤醒清理器；前端无需等待全部文件删除才收到受理响应。由独立后台清理循环持久推进，实施者可选择与现有服务同进程的独立循环或专用 worker，但必须随 `pnpm dev` 和完整测试栈启动，原生部署说明须写明如何启动，不能依赖用户下次访问、export render 循环空闲或手工 maintenance。

对候选素材在协调锁下重新确认引用；无引用版本才移除素材元数据，并在同一事务持久化实际 key 的待删工作。素材一旦判定删除并撤销可引用的数据库身份，其他请求不能继续为它建立有效引用。文件删除只能发生在该事务提交后，且必须可重试。

每个实际 key 的安全检查也要与可能新增引用的路径协调；不能“先查无引用、释放保护、之后随意删除”。不可复用已退休的 key 重新发布文件。共享项只解除本作品引用，不复制或删除共享文件。

成功后逐项落库；若文件删除成功但确认状态前进程退出，再次删除缺失文件仍成功。删除失败保留任务和错误并自动重试；用户看到“作品已删除，部分文件尚未清理”，不能看到全部成功。自动重试使用有上限的退避间隔并持续尝试，日志可定位任务／错误；手动重试可提前触发，不绕过权限、租约或检查。

设计者选择：重试间隔从数秒逐步增加，最大不超过 5 分钟，具体退避参数由实施者确定；不设到次数即放弃的终止状态。用户端只返回安全错误摘要，完整文件路径及内部错误留服务日志。

## 并发与维护一致性

以下是不变量；锁顺序、事务隔离策略、死锁重试细节由实施者在计划中设计并验证，不限定某一条 SQL。

1. 恢复与删除互斥：恢复先提交则删除因正常状态拒绝；删除先提交则恢复 NOT_FOUND。不会恢复出缺素材的作品。
2. 导出请求读取快照后，在任务入库事务中重新验证作品正常且版本可用，并与永久删除互斥；删除完成后不能插入新导出或悬空引用。worker Claim 与删除的活动任务检查不能留竞态窗口。
3. 新建／保存／复制作品、模板／资源发布或版本创建、导出引用的写入，与素材回收共享协调协议。素材锁和引用检查使用能够看见最新已提交引用的查询，避免 MySQL 旧快照误判无引用。
4. 两个删除任务涉及同一素材时，不能重复错误删除共享文件；最后一个引用释放后至少有一个持久化任务负责回收。依赖存在的 asset foreign key 有助于保护，但不替代完整引用协调。
5. 所有新增数据库／文件写入路径沿用维护门禁与 WriterGate；后台清理单次工作持 writer lease。维护备份／GC 取得独占锁后，清理器必须停止写入，不能与一致性快照并行修改。
6. 维护 GC 可以先删除同一待清理文件，后续 worker 按文件缺失成功收敛；不能误删其他引用或让任务永久失去完成条件。候选素材行被 GC 移除时，worker 仍利用接受事务中持久化的 key 核查并清理残留文件，不能仅凭素材行不存在就认定物理清理完成。
7. 不从 HTTP 请求里调用全局 `GC.Run`、取得全局独占写锁或清理整盘。两个入口及维护 GC 的素材回收规则应复用，保留维护 GC 的 30 天触发条件与其他现有职责。

## 接口与契约

建议的路由职责如下，确切命名由实施计划固定，保持现有 DeleteProject 的软删除语义：

| 方法和路径 | 职责 |
| --- | --- |
| `DELETE /api/v1/projects/:id/permanent` | 所有者发起或取得既有删除任务 |
| `DELETE /api/v1/admin/projects/:id/permanent` | 管理员发起或取得既有删除任务 |
| `GET /api/v1/project-deletions` | 当前用户未完成清理列表，支持分页 |
| `GET /api/v1/project-deletions/:id` | 当前用户删除任务状态，含完成结果 |
| `POST /api/v1/project-deletions/:id/retry` | 当前用户手动重试 |
| 对应 `/api/v1/admin/project-deletions` 的列表、详情和 retry | 管理员查询／重试 |

任务接口 `:id` 是删除任务 ID，永久删除入口 `:id` 是作品 ID。禁止同路径歧义。列表只返回鉴权允许的最小元数据；管理端筛选可扩展现有 AdminProjects 查询，但不能改变其他 ListQuery 消费方的默认行为。

空闲状态可低频轮询，有未完成任务时建议每 2 秒查询，离开页面停止页面轮询；后台清理不受影响。请求错误、会话过期复用现有处理；响应晚到必须按任务／账户身份处理，不能关闭另一作品对话框或污染另一账号缓存。

IDL 为契约源，修改 HTTP、common DTO、RPC call/payload 后运行 `pnpm contracts:generate`，提交生成结果。管理员 action 的目标字段及 core wiring 需同步设计，不手改生成物。业务冲突沿用可映射 409 的 CONFLICT 或补齐映射；状态响应遵循现有 requestId/reply 结构。

## 本地草稿与页面状态

本机用户发起删除并收到受理后，清理对应 userId/projectId 的 IndexedDB 草稿；草稿清理失败不能伪造服务端失败或重复提交删除，单独提示。多标签页用事件或 BroadcastChannel 通知旧编辑器停止该作品 autosave，清理后不能再写回旧草稿；刷新后服务端 NOT_FOUND 不会创建同 ID 作品。

管理员删除或其他设备操作不承诺远程抹除浏览器数据。旧编辑器在得知作品不存在后停止保存并告知无法继续保存至原作品；不把 NOT_FOUND 当成成功保存，也不自动重建同 ID。

成功后刷新相关作品数、回收站、未完成任务、管理员作品／导出／概览缓存。最后一件删除后分页退回有效页；不能只显示某页为空而遗漏其他作品。清理失败状态刷新后仍存在，恢复和再次发起删除不可用，仅可重试清理。

## 部署与迁移

新增向前迁移创建任务和工作记录等必要结构，不重写已发布的初始迁移。最小任务记录不能对已删除作品建立阻止删除的外键。保留 owner／actor 与现有用户模型的兼容性。

维护检查、备份和恢复的显式表列表、schema 版本判定、集成测试启动器和开发启动器同步更新。任务状态、执行租约和逐文件记录必须随数据库备份恢复；恢复后清理器能接管过期租约。清理器遵守维护锁，备份不会捕获“数据库认为文件仍在、文件却已被并行删除”的不一致状态。

操作顺序：先停相关服务并执行迁移，再启动包含清理器的新版本。不要允许旧 maintenance 工具在新 schema 上跳过任务表生成不完整备份。部署文档说明文件清理故障的日志定位和恢复方式。

## 验收标准

- 两个入口均只允许已软删除作品；本人、跨用户、普通用户调用 admin、禁用／需改密账号等权限路径验证明确。
- 覆盖用户 30 天内删除、管理员清理超过 30 天遗留记录，未知作品与已受理任务重复请求，正常作品状态冲突。
- 主记录、历史、导出快照及 project/project-history/export 引用完整删除；损坏文档不阻止清理；审计与接受事务原子提交。
- 使用真实临时 FileStore 断言文件不存在：当前独占素材、只在历史中使用的素材、原图／标准化／预览图、导出 PNG／预览文件。
- 共享正常作品、其他回收站作品、历史、导出及资源版本的素材保留；其他作品可继续打开和导出；多素材版本、重复 key、空 key、缺失文件正确处理。
- 注入文件删除失败、数据库回滚、状态落库前崩溃、重启、租约过期与重复重试，最终无孤儿任务或错误成功，未完成状态可重新查询。
- 受控并发测试覆盖恢复、导出创建／领取、其他作品或资源新增引用、两个删除任务共享素材；不依赖计时碰运气。
