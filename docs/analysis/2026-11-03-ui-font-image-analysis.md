# 控件细节、字体与图片上传分析

日期：2026-11-03。阶段：只读调查与改进建议，尚未实施本轮产品修改。

用户用途：三四句短句、歌词海报；希望至少支持电脑常见字体。保留现有清新配色与整体气质。前一轮四项修复的未提交修改仍保留，本报告不覆盖它们。

## 证据边界

- 阅读了用户截图与真实图片、当前源码、相关单元/集成/E2E 测试和 Base UI 官方文档。
- 附件 `.jpg` 被 `file` 与 ImageMagick 均识别为 PNG，1152×2048，后者可以解码；本轮没有向用户业务环境重新上传该文件。
- 实跑 fontfile 的 `TestFontActualWeightAndGlyphCoverage` 与 `TestDocumentMissingGlyphIsExplicit`，均通过，确认 Inter 缺中文字形的检测路径。
- 未读取业务数据库的实际字体清单，不能把 bootstrap 的两种家族说成用户当前环境恰好只有两种。
- 本轮没有运行新的业务浏览器截图对比；焦点与箭头原因来自截图及 CSS/调用链核对。

## 1. 搜索框蓝色焦点

`TemplatePicker.tsx` 与 `BackgroundPicker.tsx` 使用 `TextInput variant="bare"`。`Input.tsx:25-28` 仅给 field 变体附加 Input.module.css 的 `.text`；bare 不带组件类。主题焦点规则只在 `.text:focus`，页面 `.picker-filters` 虽补了边框/背景，却没有覆盖焦点 outline。浏览器原生焦点因此露出，与截图吻合。

建议所有输入变体共享最小的焦点基础样式，再用变体决定尺寸、边框与背景；搜索使用现有 `--fp-focus-line`、`--fp-focus-shadow`。保留键盘可见焦点，不单独 outline:none。同步审计后台搜索、Textarea、输入组焦点，防止只修一个弹窗。

验收：Tab、鼠标点击和 Dialog 初始聚焦都显示绿色反馈；bare 搜索、普通表单、紧凑输入一致，无尺寸变化。

## 2. Select 左右内边距不均

`Select.module.css:18` 对文字额外 `padding-inline-start:4px`，`:28` 对图标 `margin-inline-end:-6px`。页面还各自设置 8/9/10px padding，两者叠加使左右失衡。之前的测试甚至要求箭头距右边框不超过 4px，这是旧的“匹配原生控件”目标，本轮应按用户反馈修改该目标。

建议让触发器持有统一的逻辑内边距，文字与箭头分别占正常内容区域；去掉上述偏移。默认建议 10px，紧凑建议 8px，作为方案默认值而非用户已同意的数值。图标尺寸保持克制，长文本只截断 Value，不挤压箭头。保留前轮整行可点击修复。

验收以实际可见文字/图标的左右边距平衡为准，覆盖字体、字重、缩放、分类、长名称与触屏；更新旧 caret inset 用例，不能为了让旧测试通过继续保留错误视觉。

## 3. 错误提示统一为 Message/Toast

当前约 43 处 `<Status tone="error">` 分散在页面、表单与弹窗，没有统一通知管理。直接把 Status 改成每次 render 弹 toast 会重复触发，尤其字形检测随文档变化、网络重试和多个组件同时感知同一错误。

建议复用当前依赖 `@base-ui/react/toast`，在 `@fastposter/ui` 封装主题化 Message/Toast 和统一通知入口。无需为了通知再引入一整套组件库。

建议策略（尚待设计确认）：

| 事件 | 展示行为 |
| --- | --- |
| 上传/删除/导出创建失败等一次性操作 | 轻量 toast，带关闭；可恢复操作提供重试 |
| 查询失败 | 同一资源/错误去重；保留页面重试入口，不因每次重绘重发 |
| 表单字段错误 | 字段关联信息保留，必要时统一 toast 概括；不能把错误位置丢掉 |
| 保存冲突、离线、持续缺字 | 持续状态仍可找到；toast 可常驻/更新，不能仅几秒后消失 |

沿用暖白、深绿、淡绿边框、浅赤陶错误色；建议普通通知 4–6 秒，最多并列 3 条，悬停/聚焦暂停；错误根据恢复条件延长或常驻。数值属于本次建议。

通知不抢走编辑器焦点。需验证 Dialog/BottomSheet 内触发的 toast 不被遮罩遮住、不因模态 aria-hidden 对读屏器不可见；重复字体检查不刷屏，账户切换清除旧账户通知。避免请求拦截器与消费组件各报一次。

## 4. 字体数量与缺字

### 现状

- `builtin_fonts.go:90` bootstrap 仅声明 Noto Sans SC（400/700）和 Inter（400/700）；还支持后台上传发布字体。
- `TextPanel.tsx:59-61` 直接 apply，尚未先验证候选字体对选区文字的覆盖。
- `ProjectWorkspace.tsx:115-135` 在文档改变后 500ms 调用 CheckFonts；缺字时记 glyphError，`:313` 阻止导出。
- `fontfile/coverage.go` 按实际字体、字重、斜体遍历文本节点；`font.go:201-223` 查询真实 GlyphIndex，报告最多 12 个缺失字符。
- export worker 也运行 CheckDocument，单纯隐藏前端错误不能让导出正确。
- `FontRegistry.ts` 通过同源字体资产建立 `fp_<assetId>` FontFace；文档存储字体资产版本。仅增加 CSS 系统字体名称不符合现有可重现导出链路。

Inter 的英文通过、中文缺字是已验证的真实覆盖不足。对用户某一次切换是否也是 Inter、上传字体或其他特殊字符，仍需要该次所选字体名和完整缺字内容，不能断言所有缺字提示都是同一原因。

### 建议的选择行为

先确定应用范围（选区、光标后续文字、整块文字），再对候选字体与目标文本/样式做覆盖检查。短句适合低成本预检；缺字字体在菜单中可解释地标为不可用，点击时不改变已有排版。提示给出具体缺字和可用中文字体入口。

字体下拉可做可搜索的 Combobox，展示家族、适用中文/西文和真实字体预览。字重显示该字体实际支持的版本，换字体时保留可用字重或明确选择替代，处理残留粗体/斜体 mark，不能伪造不存在的字形。

对混合歌词中的中文与英文，首选支持中文的字体用于全句；也允许只给选中的英文设置 Inter。自动按字回退到另一字体是更大改动，需要统一文档、字宽、行高、模板包、字形校验与导出，不能先交给浏览器偷偷 fallback。

### “电脑常见字体”的两种接入路径

1. **内置可托管字体 + 授权导入**：覆盖常见黑体/宋体/楷体/手写风格，预览和服务端导出共用同一文件。Noto Serif CJK、霞鹜文楷可作为新增候选，具体字重、文件大小、许可与覆盖应逐一验证。
2. **直接选择本机已安装字体**：需要系统字体访问/导入。Local Font Access API 需要用户授权且浏览器兼容有限；本地能显示并不意味着远程导出 worker 可取得同一字体。要么合法导入相同文件，要么另行设计本机渲染/导出路径，不能仅列出字体名便承诺可导出。

Windows/macOS 常见的具体字库与开放字体的风格近似不等于同一字体。电脑安装许可也不自动包含将字体文件复制到服务器公开分发的权利；Microsoft 官方区分 CSS 本机使用与自托管。若必须支持某一款具体字体，需要核对相应授权及部署方式。

扩充时还需处理当前 ListFonts 的 LIMIT 100（按字面记录，不按家族）、单文档 100 字体引用上限、20MiB 上传/30MiB 解码限制和加载缓存。CJK 字体较大，新增前应按实际文件验证，不承诺一次打包上百款。

## 5. 右侧设置使用左右加减的 InputNumber

当前已有 Base UI NumberField，但封装只渲染 Input，没有 Group/Decrement/Increment。因此不需要换库；可以扩展现有封装，保留上一轮已修复的 raw 草稿、Enter、Escape、方向键、外部撤销同步。

建议提供显式 stepper 变体，在用户指定的字号、行高、字距和数值文字效果启用，结构是减号 / 数值 / 加号。普通后台输入不必全部一刀切。

| 设置 | 展示与步进建议 | 现有边界/语义 |
| --- | --- | --- |
| 字号 | px；1 | 1–4096 |
| 行高 | 倍；0.1 | 0.5–5 |
| 字距 | px；1 | -100–1000，允许负数 |
| 透明度 | 可考虑 %；5% | 模型仍为 0–1，步长 0.05 |
| 内边距/描边/模糊/偏移 | px；1 | 沿用现有动态 max 与范围；阴影偏移允许负数 |

单位与透明度百分比属于建议而非已批准的新语义。到边界禁用对应按钮；点击不提交外层表单，不抢丢 Tiptap 选区。手机保障点击目标和输入宽度，空间不足时将两个字段改为单列，不压缩成难以点按的小按钮。颜色选择不改造成数字步进器。

验收需补“点击 +/- 后海报正确变化”的真实用例；仅测 fill 和键盘箭头不足以证明新按钮可用。还应测试达到边界、混合选区值、小数精度与一次撤销的操作粒度。

## 6. 后缀与实际格式不一致的图片

附件事实：名称以 `.jpg` 结尾，但真实 PNG，1152×2048。当前 `assets/service.go` 先 Probe 识别真实格式，随后 `safeName()` 在 `:67-68` 比较扩展名并返回该报错，尚未进入 Normalize。HTTP 集成测试 `assets_http_test.go:115-118` 还明确要求这种场景为 422，说明是既有策略，不是偶发损坏。

建议把真实内容作为格式依据。对于支持的静态 PNG/JPEG/WebP，只要内容验证和解码通过，后缀不符可自动纠正，继续现有标准化为 PNG 的流程；不要要求用户手动改名，也不应强制把 PNG 再有损转成 JPEG。

保留文件名清洗、真实格式白名单、尺寸/字节限额、动画限制、结构校验和解码验证。存储与下载的 MIME/扩展名应与实际内容一致，必要时在元数据保留原始文件名。任意文本假装 jpg、损坏图片等仍拒绝。

测试应把“合法 PNG 命名 jpg 返回 422”改为成功，并验证输出尺寸、规范化文件和 MIME；同时保留伪造内容/损坏图片拒绝测试。附件可作为人工验收样本，自动化使用小型可维护的同类 fixture 即可。

## 建议推进顺序

先处理焦点、箭头和图片格式策略；再扩展数值 stepper 与统一通知；字体在明确“内置风格”还是“本机具体字库”后确定接入路线，并把选择前预检与导出一致性一起完成。以上是本次分析建议，尚未执行新一轮产品修改。
